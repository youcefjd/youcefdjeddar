title: "A Signed Audit Trail Doesn't Prove Your AI Agent Did the Right Thing"
date: 2026-08-31
description: "AgentGate is a useful example of why recording an agent's actions and governing those actions are two different problems."
---

"Signed audit logs" sounds like a solved problem. Hash the record, sign it, done—now nobody can dispute what happened. That framing is backwards for AI agents specifically, because the interesting question was never whether the log is tamper-evident after it's written. It's whether the thing producing the log is something the agent can influence, skip, or route around in the first place. An audit trail and a governance control are not the same thing, and it's easy to mistake one for the other the moment cryptography gets involved.

A small open-source project called [AgentGate](https://github.com/Clawdlinux/agentgate)—a gateway that generates signed receipts for actions an AI agent takes against SaaS APIs like GitHub, Slack, and Google Workspace—turned out to be an unusually good vehicle for making that distinction concrete. I want to take its documentation at its word, walk through what it actually establishes, and then push on the question that matters once you're thinking about giving an agent delegated authority over something consequential: does receipt-generation live outside the agent's control, or is it a logging call the agent has merely agreed to make?

I've run into a version of this same problem before, in a completely different domain. I [built a small multi-agent system for catching drift in a market-data pipeline](https://youcefjd.github.io/youcefdjeddar/teaching-agents-to-watch-a-pipeline/), organized around one rule: agents can see everything, but the audit trail is what a compliance reviewer actually trusts—not the agent's own account of what it did. An agent's self-report isn't evidence. What earns a skeptical reviewer's trust has to be independently verifiable, separate from the system whose behavior is in question. AgentGate is making the same bet, just applied to SaaS API calls instead of pipeline monitoring, which is why it's worth engaging with seriously instead of dismissing as another "add a hash" audit-log wrapper.

Stripped down to what actually matters for this argument, here's what AgentGate's documentation establishes: the agent never holds OAuth credentials directly—the gateway holds and handles all tokens, and the agent's only interface to any upstream API is a single endpoint. Every action attempt, not just successes, commits a signed, hash-chained receipt before the response goes back to the agent. And that receipt chain is independently verifiable offline, by someone who has never seen the gateway's internals, against nothing but a copy of the log and a pinned trust file.

That last point is the one worth sitting with. Because the receipt is committed as part of servicing the request—not as a separate call the agent chooses to make afterward—an agent operating inside this architecture has no path to the upstream API that doesn't also produce the record. This is a real, structural claim about the intended design, not a guarantee about any specific deployment. The documentation itself doesn't claim otherwise: it doesn't protect against a deployment that also hands the agent direct credentials by mistake, or one that fails to force all outbound traffic through the gateway at the network layer. "The agent cannot bypass the receipt" is true of the design and false as a claim about production unless the surrounding infrastructure enforces it too.

It's worth pulling apart four properties that get flattened into one phrase when people say "audit trail":

**Non-repudiation**—proof of who or what produced a record. A signature ties a receipt to whoever holds the signing key.

**Tamper-evidence**—proof a record wasn't altered after the fact. A hash chain makes retroactive edits detectable.

**Completeness**—proof nothing was skipped. Committing a receipt for failed attempts too, plus a way to checkpoint that a stretch of the chain has no gaps, is aimed specifically at this.

**Correctness of the underlying decision**—whether the agent should have taken the action at all. Nothing above touches this. A perfectly signed, gap-free, tamper-evident log can faithfully document an agent doing something disastrous. It tells you exactly what happened and that the record wasn't doctored afterward. It says nothing about whether the action was authorized, reasonable, or consistent with policy—and to its credit, AgentGate's documentation doesn't claim otherwise. That question is explicitly out of scope.

The framing I started from—that most "agent audit trail" tools quietly assume the agent will cooperate with its own surveillance—needs to be applied carefully here rather than uniformly across the category. A voluntary logging SDK is defeated trivially: an agent that doesn't call it, or calls it with fabricated parameters, leaves no trace, because the SDK has no leverage over whether the underlying action happens at all. AgentGate's model is different in kind, not just degree—the gateway is the only path to the credential, so the receipt isn't optional telemetry about an action that already happened somewhere else; it's a byproduct of the gateway being the component that actually made the call. It would be dishonest to lump that in with tools that are just self-reported logging with a hash appended.

Where the "assumes cooperation" critique still has teeth is at the boundary between design and deployment. The guarantee depends entirely on nothing giving the agent an out-of-band path to the same upstream APIs—and that's a fact about network topology and operational discipline, not about the gateway's code. Realizing it in production requires the deploying organization to block every route from the agent's runtime to the upstream API other than through the gateway, something no gateway, however well-designed, can enforce from inside its own process. Judged strictly against what's documented, this doesn't fit the original criticism as cleanly as I expected going in. The honest version of the critique is narrower than "this tool assumes cooperation," and closer to: this guarantee is only as strong as the deployment's network policy.

The case for this kind of rigor gets stronger as agents move toward initiating actions that are hard to reverse or carry real financial consequences: updating a record that feeds a downstream decision, initiating a transfer, invoking a tool that suppresses an alert. And even taking the design fully at its word, one gap stands out for anyone evaluating something like this for a genuinely high-stakes deployment: nothing in the documentation addresses how the trust root itself gets rotated if it's ever compromised, or who owns that process. For a system whose entire value proposition rests on "verify offline against a pinned trust root," silence on how that root changes hands is a real gap, not a minor omission.

The revised version of the argument I started with, after reading the actual documentation instead of just the pitch, is narrower than where I began—and more useful for it. A signed receipt is a governance control only to the extent that receipt-generation is structurally outside the agent's reach, and on that specific point, this design earns more credit than the average "audit trail for agents" pitch deserves by default: it is not, as documented, a voluntary call the agent could simply skip. What it doesn't do, and doesn't claim to do, is settle whether the underlying action was correct, who's accountable if the signing key is compromised, or whether the surrounding deployment actually closes off the side channels its guarantees assume don't exist. Those are network-policy and key-management questions at least as much as cryptographic ones.

The broader point isn't really about this one project. It's that "we log everything and sign it" keeps getting treated as though it answers the governance question, when it only answers the evidence question. Those are different problems, and conflating them is exactly how a well-engineered audit trail ends up standing in for oversight it was never designed to provide.
